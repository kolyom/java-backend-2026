# Тема 2 — Инкапсуляция

Опираемся на твой `labs/oop/BankAccount.java`.

---

## Идея одной фразой

**Прятать данные и открывать только безопасные действия.**  
Снаружи не «крути гайки поля», а вызывай осмысленные методы.

---

## Что ты уже сделал правильно

```text
private Long balanceKopecks;     // снаружи не пишут account.balanceKopecks = ...
deposit / withdraw               // баланс меняется по правилам
нет setBalanceKopecks            // нельзя тупо выставить миллион
```

Это и есть инкапсуляция на практике, не «геттеры ради геттеров».

---

## Зачем `private`

| Без private | С private |
|-------------|-----------|
| Любой код может сломать инварианты (`balance = -5`) | Менять состояние можно только через методы класса |
| Правила размазаны по всему проекту | Правила живут в одном месте (`withdraw`) |

Инвариант счёта: «баланс не уходит в минус» (в нашей простой модели).  
Его охраняет `withdraw`, а не надежда, что все программисты будут вежливы.

---

## Геттер / сеттер — не цель, а инструмент

- **Геттер** — «можно читать» (`getBalanceKopecks`). Часто ок.
- **Сеттер** — «можно писать что угодно». Для баланса — опасно.
- **Сеттер с проверкой** — уже лучше, но для баланса всё равно слабее, чем `deposit`/`withdraw`.

Правило большого пальца:
- идентификатор, имя — иногда setter допустим;
- деньги, статус заказа, пароль — обычно **методы с правилами**, не голый setter.

---

## `this` (закрепим)

```java
public void setId(Long id) {
    this.id = id; // this.id — поле объекта, id — параметр метода
}
```

Без `this` имя параметра затенило бы поле, и ты бы написал `id = id` (бессмыслица).

## Мини-улучшение твоего класса (5 минут)

В `deposit` и `withdraw` добавь защиту от отрицательной суммы:

```java
if (amount <= 0) {
    return;        // для deposit
    // или return false; для withdraw
}
```

Сделай сам в VS Code. Это и есть усиление инкапсуляции: метод не принимает мусор.
